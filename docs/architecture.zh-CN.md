# 分层架构与项目边界

## 设计原则

整个体系采用分层设计，各层通过稳定接口协作。

| 层次 | 核心职责 | 对应项目 |
| --- | --- | --- |
| Agent Team | 业务目标、角色行为、协作关系、任务执行与反馈 | 具体业务应用 |
| MAO | 模型服务的访问使用方式，包括请求构造、调用方式与结果处理 | model-access-object |
| MSCP | 模型服务资源的获取、占用管理与归还 | model-service-connector-pool |
| Connector | 具体模型服务的协议与传输适配 | MSCP 中的服务适配组件 |

项目在仓库和维护上相互独立，运行时由 MAO 使用 MSCP。记忆、存储、
工具执行等能力按应用需要独立配套。

## 一次访问的过程

1. Agent 实例根据业务需要构造任务消息，通过注入的 MAO 使用模型。
2. MAO 整理模型能力需求和调用参数，向 MSCP 获取资源。
3. MSCP 根据能力和当前可用容量返回租约。
4. MAO 通过租约调用连接器，并将结果整理为统一响应。
5. 完成、异常、取消或关闭流式输出时，MAO 归还资源。
6. Agent Team 根据结果决定下一步业务动作。

MSCP 接收能力需求和用于归属记录的 Agent 标识。角色定义、任务分配、
提示内容和协作反馈由业务应用负责。

## 连接器、租约、会话

| 概念 | 生命周期 |
| --- | --- |
| 连接器 | 长期复用的模型服务访问对象，可持有 HTTP 客户端 |
| 租约 | 临时占用一个容量名额，通常覆盖一次调用 |
| 会话 | 应用保存的多轮交互上下文，可跨越多次租约 |

每个租约同一时刻允许一个在途调用。多个并发调用分别借用租约。
租约释放后禁止继续调用。多轮交互的历史由应用或记忆服务保存，
下一次访问时重新携带所需上下文。

## 能力配置

应用可以配置某个角色、任务和单次访问的能力要求。MAO 合并这些要求：
必需标签取并集，最小上下文取最大值，流式要求取逻辑或。附加要求会保留
已有硬约束。无法同时满足时，由资源层返回明确的能力不匹配错误。

这些配置描述模型访问需要，角色的业务行为仍定义在 Agent Team 中。

## 当前部署范围

当前实现为单个 asyncio 事件循环内的嵌入式池。需要共享容量的 MAO 和
Agent 必须使用同一个池实例。共享注册表本身不会共享容量计数。
同一个底层资源应配置为一个共享连接器；多个连接器标识的额度尚未自动合并。

机构内多个应用共享的公共池需要后续建设集中式服务接口，并定义远程租约、
过期回收、客户端故障恢复和服务端多进程的一致容量管理。当前代码尚未提供
这项部署能力。

## 框架的形成方式

借鉴 Spring 应用的服务层、DAO 和连接池组织方式，先稳定业务层、
模型访问层和资源层的接口，再从实际应用中提炼统一配置、组件装配和
生命周期管理。

当前通过构造函数注入 MAO，用应用启动代码组装连接器、池、访问策略和
Agent 实例。通用框架容器留待多个应用验证后提炼。

## 可运行示例

- `examples/proposal_team.py`：仅依赖 MAO 的写作 Agent、审查 Agent 和业务反馈。
- `examples/layered_team.py`：两个 Team 共用一个池的离线组装示例。
- `examples/openai_compatible.py`：通过环境配置访问实际模型端点。

离线示例通过确定性的服务替身验证调用链和资源释放。HTTP 协议测试使用
模拟传输；实际端点的效果、容量和稳定性需要在部署环境中继续验证。
